# Разработка

Команды выполняются из корня репозитория. Нужен Python 3.10 или новее. Основной код находится в `epicrises/`; карта обязанностей — в [описании модулей](modules.md).

## Окружение и проверки

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
python -m unittest discover -s tests -v
python -m ruff check .
python -m ruff format --check .
node --test tests/frontend/*.test.mjs
```

Python-тесты используют правила или подменённые ответы модели. GGUF-веса и `llama-cpp-python` для них не нужны. Node.js 22 нужен только для тестов JavaScript; приложение не требует сборки или `npm install`. Проверки frontend выполняются без браузера, поэтому изменения разметки и поведения DOM дополнительно проверяются вручную.

Для отдельных подсистем:

```bash
python -m unittest discover -s tests -p test_jobs.py -v
python -m unittest discover -s tests -p test_storage.py -v
python -m unittest discover -s tests -p test_incremental_processing.py -v
python -m unittest discover -s tests -p test_extraction.py -v
python -m unittest discover -s tests -p test_citations.py -v
```

Контрактные проверки охватывают поля и цитаты, API, экспорт, очередь, хранилище, CLI и состояния интерфейса. Проверку с настоящей LLM проводите отдельно от быстрого цикла разработки: она требует весов и расходует ресурсы CPU/GPU.

## Ручной запуск без модели

```bash
LLM_ENABLED=false python app.py
```

Откройте `http://127.0.0.1:5000`. Основная регрессия: загрузить A, обработать, добавить B и снова обработать. Вторая партия должна содержать только B, а результат и цитаты A должны остаться доступными. После обновления страницы и после перезапуска приложения готовые документы сохраняют отметки обработки.

Пакетный запуск с отдельными выходными каталогами:

```bash
python process_documents.py --regex-only --input test_docs --output /tmp/epicrises-results --metrics /tmp/epicrises-benchmark.json
python add_citations.py --regex-only --input test_docs --results /tmp/epicrises-results
```

Прежняя команда `pipeline.py` переименована в `process_documents.py`; замените имя в собственных скриптах. Аргументы и коды завершения сохранены: `0` — успех, `1` — ошибки документов, `2` — ошибка запуска, `130` — прерывание пакетной обработки с сохранённым отчётом. `app.py` и `add_citations.py` не переименованы.

## Как изменять модули

### Приём документов

Проверки форматов, ZIP, размера и имён находятся в `documents/upload_reader.py`. Файловые пути, готовность и совместимость результатов — в `document_store.py`. Операции загрузки и удаления проходят через `DocumentService` и общий `SessionCoordinator`: проверка занятости, изменение файлов и сброс прогресса выполняются под одной блокировкой.

Проверяйте отказ всей партии при неверном документе, откат частичной записи и сохранность ранее загруженных файлов. ZIP должен работать и с файловыми объектами загрузки Python 3.10.

### Обработка и хранение результатов

`DocumentProcessor` определяет последовательность обработки; `JobQueue` выбирает документы и управляет выполнением. Очередь вызывает методы хранилища, включая `save_batch_report()`, и не собирает файловые пути самостоятельно.

Сохраните регрессии: новая партия не меняет байты и время записи готовых результатов; повтор обрабатывает только ошибки; запуск без новых файлов не обращается к модели; повторный активный запрос не создаёт новую задачу. Проверяйте восстановление после перезапуска, неполный комплект, старый плоский формат и имена `case.ev.md`, `case.report.md`, `case.json.md`.

Для тестового приложения передавайте временный `data_dir` и при необходимости подменённый `processor` в `create_app()`. Завершайте `app.extensions["jobs"].shutdown()` до удаления временного каталога. Общая блокировка действует внутри одного процесса; увеличение количества worker или серверных процессов требует отдельного изменения координации.

### Извлечение поля

Правила находятся в предметных файлах `processing/rules/`, нормализация — в `normalization.py`. Выбор полей для проверки относится к `analysis/field_selection.py` и `consistency_checks.py`, принятие ответа модели — к `inference/response_review.py`.

Проверяйте положительный пример, отсутствие признака, явное отрицание и координаты цитаты, где это применимо. При изменении схемы согласуйте `shared/field_schema.py`, `field_validation.py`, правило, подсказку `frontend/static/features.json`, модельные запросы и тесты. Текущий внешний контракт — 50 строковых полей; его расширение меняет формат данных.

### Экспорт и HTTP

`DocumentService.results_snapshot()` выбирает готовые результаты под блокировкой. `ExportService` и `exporting/formats.py` формируют файл после её освобождения. Проверяйте экспорт старых готовых документов во время новой обработки и сохранение строкового типа ячеек XLSX.

HTTP-параметры и ответы находятся в `web/routes.py`, ошибки — в `http_errors.py`, UTF-16-представление цитат — в `citation_view.py`. При изменении внешнего поведения обновляйте [API](api.md) и соответствующий контрактный тест.

### Интерфейс

Запросы добавляйте в `api.js`, вычисление доступности действий — в `state.js`, представление прогресса — в `jobs.js`. Компоненты получают зависимости через параметры; их сборка остаётся в `app.js`. Запоздалый ответ при переключении документов не должен заменить текущий выбор.

Для каждого изменения сначала запускайте целевые проверки. Перед передачей изменения выполните общий набор тестов и Ruff; изменения интерфейса проверьте в браузере. В тестовых документах используйте короткие искусственные фрагменты без персональных данных пациентов.

## Упаковка

```bash
python scripts/package.py
```

Архив создаётся рядом с каталогом проекта. Скрипт исключает локальные настройки, окружение, кэши, веса и стандартные каталоги рабочих данных. Если результаты размещены в другом каталоге внутри репозитория, учитывайте его отдельно при подготовке архива.
