# Разбор эпикризов

Локальное приложение для извлечения 50 структурированных полей из эпикризов в Markdown.
Регулярные правила находят значения, статистические проверки выделяют спорные поля,
а локальная LLM уточняет их. Результаты можно просматривать вместе с цитатами и выгружать
в JSON, ZIP или XLSX.

## Устройство проекта

Основной код собран в одном пакете `epicrises` по этапам работы:

```text
epicrises/
├── documents/    приём, проверка и хранение документов
├── processing/   очередь → правила → анализ → LLM → цитаты
├── exporting/    подготовка JSON, ZIP и XLSX
├── web/          сборка приложения, сессии и HTTP API
└── shared/       настройки, схема 50 полей и файловые операции
```

Это модули одного приложения. `DocumentService` управляет документами,
`JobQueue` запускает обработку через `DocumentProcessor`, `ExportService` получает
снимок готовых результатов и создаёт файл. `web` связывает эти операции с HTTP;
`frontend/` содержит интерфейс, `cli/` — консольные сценарии.

Веб и CLI используют один `DocumentProcessor` из `processing/processor.py`.
Подробная карта и места для изменений: [модули](docs/modules.md).

## Запуск

Нужен Python 3.10 или новее. Фронтенд использует ES modules и не требует сборки.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

В Windows используйте `py -3 -m venv .venv`, `Copy-Item .env.example .env`
и запускайте команды через `.venv\Scripts\python.exe` вместо `python`.

Для запуска только с правилами установите `LLM_ENABLED=false` в `.env`:

```bash
python app.py
```

Откройте <http://127.0.0.1:5000>. Загрузите `.md` или ZIP с документами и нажмите
«Обработать». Следующая загрузка добавляет документы в текущую сессию: при обработке
готовые документы пропускаются. Повторно запускаются только новые документы и документы
с ошибкой. Если все результаты готовы, кнопка обработки отключена.

Выбор документа открывает таблицу полей и исходный текст. Наведение на значение
подсвечивает цитату, нажатие закрепляет её. В панели сохранения доступны отдельный
результат и весь обработанный набор.

### Локальная модель

```bash
python -m pip install -r requirements-ml.txt
```

Получите [Qwen2.5-3B Instruct GGUF](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct-GGUF)
и задайте в `.env`:

```dotenv
LLM_ENABLED=true
MODEL_PATH=models/qwen2.5-3b-instruct-q4_k_m.gguf
```

Веса не входят в репозиторий. `MODEL_PATH` может быть абсолютным; относительные пути
считаются от корня проекта. `MODEL_GPU_LAYERS=-1` запрашивает доступное GPU-ускорение,
`0` использует CPU; поддержка зависит от сборки `llama-cpp-python`. При сборке пакета
из исходников требуется C/C++ toolchain.

Если LLM включена, отсутствие модели считается ошибкой запуска обработки. Автоматического
переключения на регулярные правила нет. Режим без LLM явно указан в интерфейсе и отчётах.

## Настройки

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `LLM_ENABLED` | `true` | Уточнять значения и цитаты локальной моделью |
| `MODEL_PATH` | путь из `.env.example` | GGUF-файл модели |
| `MODEL_CONTEXT` | `8192` | Размер контекста |
| `MODEL_GPU_LAYERS` | `-1` | Число слоёв на GPU |
| `MODEL_THREADS` | `8` | Число потоков модели |
| `MODEL_MAX_TOKENS` | `1600` | Максимум токенов ответа |
| `APP_HOST` | `127.0.0.1` | Адрес HTTP-сервера |
| `APP_PORT` | `5000` | Порт HTTP-сервера |
| `DATA_DIR` | `runtime` | Документы, результаты и секрет сессий |
| `SECRET_KEY` | пусто | Ключ подписи cookie; при пустом значении создаётся `DATA_DIR/.secret` |

Приложение работает в одном серверном процессе с одним фоновым обработчиком.
Очередь находится в памяти. После перезапуска нажмите «Обработать», чтобы продолжить
оставшиеся документы: сохранённые результаты будут пропущены. Для сохранения доступа
к прежним сессиям оставьте `DATA_DIR` и ключ подписи без изменений.

## Консольные команды

Обработка каталога без цитат:

```bash
python process_documents.py --input test_docs --output test_json --metrics reports/benchmark.json
python process_documents.py --regex-only
python process_documents.py --model /path/to/model.gguf
```

CLI обрабатывает все `.md` указанного каталога без рекурсивного обхода и пересчитывает
их результаты при каждом запуске. Этот режим нужен для повторяемых пакетных запусков.
Перед обработкой документа удаляются его прежний JSON и цитаты; результаты других
документов сохраняются. Метрики должны находиться отдельно от каталога результатов.

Добавление цитат к уже готовым JSON без изменения значений:

```bash
python add_citations.py --input test_docs --results test_json
python add_citations.py --input test_docs --results test_json --regex-only
```

Коды завершения: `0` — успех, `1` — ошибки отдельных документов, `2` — ошибка запуска.
Команда `process_documents.py` при Ctrl+C сохраняет промежуточный отчёт и возвращает `130`.

Прежняя команда `pipeline.py` переименована в `process_documents.py`: обновите её имя
в скриптах запуска. Аргументы, форматы результатов и коды завершения сохранены.
`app.py` и `add_citations.py` запускаются как прежде.

`reports/benchmark.json` содержит время всей партии и каждого этапа, количество попыток,
успехов, ошибок и оставшихся документов, изменения полей и сводную статистику.
`average_seconds_per_document` включает неуспешные и прерванную попытки;
`average_successful_document_seconds` — только успешные. Ленивая загрузка модели входит
во время первого документа, которому понадобился инференс.

## Данные и совместимость

Новые веб-результаты хранятся в `runtime/<сессия>/results/<имя.md>/`:

| Файл | Содержимое |
|---|---|
| `result.json` | 9 групп, 50 строковых значений |
| `evidence.json` | Значения, цитаты и координаты |
| `report.json` | Этапы, изменения и предупреждения |

Основной JSON записывается последним. Неполный комплект остаётся необработанным.
Готовые результаты прежнего плоского формата (`<имя>.json`, `<имя>.ev.json`,
`<имя>.report.json`) читаются без переписывания и повторной обработки.
Проверки совместимости описаны в [System Design](docs/system-design.md#хранение-и-совместимость).
Экспорт JSON сохраняет прежний формат, внутренние служебные файлы в него не попадают.

`batch-report.json` относится к последнему запуску обработки новых документов.
Загрузка или удаление документов удаляет этот отчёт и сбрасывает прогресс, сохраняя
результаты остальных документов. Повторный запуск без новых документов не меняет отчёт.

`test_docs/` содержит пример входного документа, `json1000/` — сохранённый контрольный
набор результатов. Эти данные сами по себе не подтверждают точность на независимой выборке.

## Проверки

```bash
python -m pip install -r requirements-dev.txt
python -m unittest discover -s tests -v
python -m ruff check .
python -m ruff format --check .
node --test tests/frontend/*.test.mjs
```

Node.js 22 нужен только для тестов JavaScript. Автоматические проверки не загружают LLM:
они проверяют правила, API, очередь, хранилище, интерфейсные состояния и контракты модели
с тестовыми ответами. Для проверки качества реального инференса нужен отдельный запуск
с GGUF. GitHub Actions запускает эти проверки при push и pull request.

Архив исходников создаётся командой `python scripts/package.py`. В него не включаются
локальные настройки, веса, виртуальное окружение, кэши и результаты пользовательских сессий.
